# Foundation business and fulfillment module

The opt-in `src/modules/business` module extends the existing Node foundation. It preserves the foundation runtime, operator sessions, namespaced routes and protected Python economy. It does not install another wallet, scheduler, operator credential or root Python package.

Set `WIDEMIND_BUSINESS_ENABLED=true` with `WIDEMIND_PROFILE=foundation` to register the business and website roles. Without that flag the existing foundation remains unchanged. Configure the separate real-provider tools and commerce settings described in [BUSINESS_TOOLS.md](BUSINESS_TOOLS.md), [RUNTIME_ECONOMY.md](RUNTIME_ECONOMY.md) and [BUSINESS_UI.md](BUSINESS_UI.md). Missing providers remain unavailable; enabling a module does not qualify credentials or fund a run. Existing Node web/worker and Python accounting/reconciliation processes remain independent.

## Durable workflow

Operator commands enter the core's authenticated, deduplicated event inbox. Paused/stopped runs retain them without sending mail, creating checkout sessions or invoking a model. On resume, free local selection applies commands idempotently to namespaced `business_*` tables. Sender-authenticated Gmail messages use the same intake/acceptance transitions, with message deduplication scoped to the run. Unstructured or invalid messages require clarification; customer text cannot change credentials, runtime authority or financial records.

The registered research service validates topics, unique sections, source counts and HTTPS URLs. Normal module construction also checks the owner's exact source-host allowance, configured fallback sources, complete input/token bounds and explicit model prices before an offer. Service definitions are extensible; business policy selects capabilities, service prices, goals, scoring weights, cumulative experiment allowance, job cost ceilings, capacity, quote validity and turnaround. Outbound/discovered opportunities require an identified customer, a concrete HTTPS relevance reference, explicit outbound permission and respect for opt-outs. Offers rank by configured priority, expected contribution and goal fit before consuming the experiment allowance. Estimates and quote allocations are not wallet funds or reservations.

Quotes freeze scope, price, cost ceiling, expiry and turnaround. Prices must meet the protected Stripe commerce bridge's exact USD-cent and amount limits. Acceptance requires the owning customer identity and actual evidence reference, an offered/unexpired quote, open capacity and observed operating credit. Repeating the same acceptance creates one order. The worker proposes a centrally authorized `commerce.checkout` action, then emails the actual checkout URL. Customer payment is accepted only from the protected ledger's verified order observation.

Verified payment permits proposing research; it does not itself authorize spending or create a firm delivery deadline. The foundation reserves and verifies the paid action first. A known completed research receipt is independently checked against agreed sections, unique sources and citations before its artifact is persisted. Only then does the module persist an immutable deadline from the gateway's durably recorded successful dispatch time plus the agreed turnaround, send the commitment and deliver the attachment. Recovery retains that original dispatch time and cannot extend the deadline. A legacy receipt without trustworthy dispatch timing retains its checked artifact for operator review instead of inventing a deadline. The gateway rechecks current payment, frozen scope, runtime intent and policy immediately before paid dispatch. Paid failures and unknown outcomes remain core accounting/recovery records; the module does not silently rework them.

Gmail acceptance alone leaves the order awaiting acknowledgment. Only a trusted inbox receipt's independently authenticated delivery update, matched to the original attachment action and order, creates durable delivery evidence. `commerce.fulfill` independently checks that evidence before recognizing fulfillment through the existing economy. Delivery and cash/earned-revenue records remain separate. Explicit cancellation does not issue a refund or erase costs.

Payment observations are bounded to one order per selection. Actionable creation/delivery stages take priority; a persisted fair cursor also refreshes terminal orders and waiting payments, so later refunds remain visible. Financial evaluations append verified receipts, refunds, earned revenue, fees and measured runtime tool charges. Contribution remains unavailable while costs are provisional or incomplete; tool-level contribution does not establish full business profitability or account for undisclosed infrastructure/development expenses.

## Integration boundaries

`BusinessService.selectWork(snapshot)` returns a Candidate or a waiting decision. It never sends mail, creates checkout sessions, calls a model, posts earned revenue or reserves money. Its only asynchronous dependency is a bounded free protected-ledger observation. After that observation it rechecks the runtime revision before changing state. Local intent/receipt updates are idempotent; the core fences action planning and event acknowledgment against newer controls. Unknown external actions stay in core reconciliation and are not blindly repeated.

The tool IDs are `gmail.read`, `gmail.send`, `research.collect`, `commerce.checkout` and `commerce.fulfill`. Stable stage work keys bind each business intent to a single core action. Money at all module boundaries is an exact decimal string; times are ISO UTC. Provider credentials and opaque reservation authorizations do not enter business snapshots or public activity.

The protected console is `/operator/modules/brief-business/console`. Its API is `GET /api/modules/brief-business/console?runId=<uuid>&collection=orders&offset=0`; supported collections are opportunities, orders, effects and events, with 500-record pages and authoritative run-wide counts. Search/filter scope is the returned page. Orders prioritize outstanding work, and quotes/customers follow visible records. Related records/counts use one SQLite read snapshot. `GET /api/modules/brief-business/order?runId=...&orderId=...` returns a private artifact; the SSR console also accepts `orderId`. Order payment values are explicitly cached historical observations with observation timestamps; current financial summary is null when the economy is unavailable.

`POST /api/modules/brief-business/command` accepts `{runId,requestId,command,...}` with core session, exact Origin and CSRF. Commands are `intake`, `accept`, `policy`, `wake`, `sync-inbox`, `resolve-hold` and `opt-out`. Intake uses `service`, `scope`, `customerEmail`, optional `origin/sourceReference/priority`; acceptance uses `quoteId/customerEmail/evidenceReference`; policy uses `policy`; hold resolution uses `orderId/decision/evidenceReference`. SSR forms supply `scopeJson` or `policyJson`. A 202 response records a durable intent; the worker's private command result records whether the requested transition was valid. Use stable request IDs on transport retries. API handlers perform no business/provider effects. Trusted external inbox scheduling can enqueue the same `sync-inbox` intent without keeping a browser open; see the configured CLI/runbook.

Public output consists only of configured service descriptions and deliberately selected completion events. Customer identities, messages, scopes, artifacts, action receipts and internal evaluations remain private.

## Verification and remaining qualification

`node --test test/business.test.ts` covers queued controls/deduplication, unavailable or stale payments, stop during observation, authorization before deadline/commitment, inbox pagination, exact processor prices, source preflight, combined prioritization, old outstanding records, fair terminal refunds, run-scoped Gmail deduplication and a concurrent WAL writer. The separate integration, commerce, tools and UI suites exercise their actual implementations with explicitly offline provider fixtures. [BUSINESS_DEMO.md](BUSINESS_DEMO.md) documents the reproducible integrated offline demonstration.

For the trusted one-shot scheduled-mail command and deployment cadence, see [BUSINESS_SCHEDULING.md](BUSINESS_SCHEDULING.md). Exact protected commerce RPCs and account/mode requirements are in [ECONOMY_RUNTIME_BRIDGE.md](ECONOMY_RUNTIME_BRIDGE.md).

These are local implementation checks. Real mailbox delivery/acknowledgment, provider charges, signed Stripe sandbox/live records, deployment isolation and an independent paying customer still require owner-provisioned accounts and controlled qualification. No test fixture establishes live earnings or autonomous profit.

# Recovering an uncertain Stripe checkout

Checkout creation durably stores its scoped request before contacting Stripe. Ordinary retries reuse the original idempotency key during the first 23 hours. Stripe may later expire the key; another POST after that point could create a duplicate checkout. This recovery path **only reads existing provider objects** and never creates a session or directly posts money.

The operator can call `POST /v1/checkouts/{request_id}/recover`, or run `widemind-economy recover-checkout REQUEST_ID` with the normal economy configuration. The synchronous adapter method is `StripePayments.recover_checkout(request_id)`.

Recovery requires the existing local request. It checks the configured Stripe account and mode, reads a complete bounded list of sessions within the original request's safe creation period (five-minute clock allowance around its first 23 hours), and matches the scoped request hash in both `client_reference_id` and service-authored metadata. It then fetches the single matching session again and verifies its identity, USD amount, mode, status, creation time and request hash against the durable claim. Metadata or an incoming webhook alone cannot bind an unrelated payment. Missing, ambiguous, mismatched or incomplete results fail closed and leave the request unresolved.

A completed or expired Stripe session may no longer have a hosted URL. Recovery still binds that session ID, with a null URL, so it remains eligible for normal authenticated reconciliation. A later call to ordinary checkout creation returns the existing binding and cannot POST another session. A returned Checkout session or completed status is not settled money: `POST /v1/payments/{payment_id}/reconcile` independently verifies real available balance transactions before a positive cash component can post. The original customer/job binding remains local and immutable.

A webhook can arrive before a lost checkout response has been durably bound. It remains retryable rather than creating credit from its metadata. Recover the original request, then let the durable webhook worker or explicit operator reconciliation retry against the established binding. Do not create a replacement request ID to hide an uncertain external effect.

The recovery scan has the same provider safeguards as ordinary reconciliation: at most 256 HTTP requests in one nested operation, a 60-second monotonic operation budget checked before requests and between response chunks, individual HTTP timeouts bounded by remaining time (maximum 20 seconds per phase, 10 seconds to connect), no redirect following, and a 2 MiB response-body limit. Budget or pagination exhaustion never applies a partial payment snapshot; retry/reconciliation remains necessary. A blocked read can consume its already-assigned phase timeout before the next monotonic check. These limits prevent a long provider history from holding a worker indefinitely, but an unusually large account history may require operator investigation rather than automatic recovery.

This feature's tests use explicit HTTPX Stripe fixtures, including lost responses, recovery beyond the idempotency window, completed sessions without URLs, record mismatches, incomplete pagination, early webhooks, delayed verified-event processing, time/request/body budgets and concurrent adapter calls. They do not establish a real sandbox or live payment. Actual verification still requires the account credentials, signing secret and network/ingress setup documented in [economy setup](ECONOMY_SETUP.md).
